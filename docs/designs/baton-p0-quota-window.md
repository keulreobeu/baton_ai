## Problem Statement

Claude Pro와 ChatGPT Plus(Codex)는 사용 시점부터 5시간 사용량 창이 열린다고 가정한다(공급자 정책은 미실측, 아래 가정 A1).
늦게 첫 요청을 보내면 리셋이 업무 시간 한가운데에 걸린다. BATON P0는 **매일 07:00과 12:05(KST)에 Claude·Codex에 최소
요청을 1회씩 보내 창 시작 시각을 고정**한다. 07:00 창은 약 12:00, 12:05 창은 약 17:05에 리셋되어 업무 시간 창 두 개를 확보한다.
작업 분배·라우팅은 P0가 아니다(P1).

## What Makes This Cool

- 사람이 알람 맞춰 "hi"를 치던 일을 Python 제어면이 대신하고, 추정 리셋 시각을 신뢰도와 함께 `baton quota-window status`로 보여 준다.
- 같은 원장의 창 상태 표가 P1(Codex/Claude/Antigravity 작업 스케줄러)의 "어느 구독이 여유 있나" 판단 입력이 된다.

## Constraints

- 구독 로그인만 사용. API 과금 경로(아래 C2)가 감지되면 핑 0회. `--bare`, `--dangerously-skip-permissions` 금지.
- 실제 모델 호출은 실핑 1회/provider/트리거뿐. 테스트·dry-run은 fake runner로 모델 호출 0.
- 기본 `enabled=false`, `dry_run=true`. 실핑 활성화·Windows 작업 스케줄러 등록은 별도 사용자 승인. 등록 명령은 출력만.
- Windows 11 native, 표준 라이브러리만. Windows Python은 tzdata가 없어 `zoneinfo("Asia/Seoul")`이 실패할 수 있으므로 KST는 고정 UTC+9(한국은 DST 없음).
- PC가 꺼져 있으면 실행 불가. 클라우드로 우회하지 않는다.

## Premises (확정, D3·D5 — P0 범위만)

1. P0 = Quota Window Scheduler(07:00·12:05 KST, Claude·Codex). Antigravity는 5h 창 구조 미확인으로 P0 제외(P1).
2. 창 상태를 모르면 그래도 핑한다(열린 창 안의 핑은 리셋을 바꾸지 않고 소량만 소모). 단 구독 로그인 미확인·API 과금 경로·이미 핑한 슬롯이면 0회. v6 S04("미확인이면 0회")를 이 목적에 맞게 변경.
3. 늦은 핑은 리셋 시각을 민다 → 트리거별 허용 지연을 둔다(아래 T1).
4. 조건부 PC 종료는 P0에서 제외(기본 OFF 유지).
5. P1 = Codex/Claude/Antigravity 작업 스케줄러(라우팅, quota 인계, ClaudeCodeProvider).
6. P0와 무관한 후속 작업(jipdam 재사용 이식, GMS 기본 비활성, 프로파일 추출)은 아래 "Related Work"의 별도 Task로 관리.

## Assumptions (실측 전 설정값으로 둔다)

- **A1 창 길이·시작**: 창은 첫 요청 시각부터 5시간. provider별 `window_hours=5`, `align="none"` 설정값. 실측(1주)으로 확인하기 전에는 status에 "assumed"로 표시.
- **A2 열린 창 안의 핑**은 리셋을 바꾸지 않는다.

## Cross-Model Perspective

Codex는 사용량 한도로 실행 불가(17:13 리셋). Claude 하위 에이전트 cold read(미검증 의견):
- 세 구독의 5h 창을 하나의 예산으로 보고 quota 소진 시 실제 git diff 기반 인계로 다른 구독이 잇는 "quota-window relay"가 가장 멋진 버전.
- 현재 실제 구독 provider는 Codex 하나뿐이고 기본 `fallback_provider="gms"`(`src/baton/managed.py:45`).
- P3(Scheduler 먼저)를 반박 → 사용자 답변(D4)으로 P0가 "창 시각 제어"로 재정의되어 해소. relay 제안은 P1로 이관.
- 검증으로 바로잡은 점: `src/baton/orchestrator.py:122-131`은 quota 시 **변경이 없을 때만** 1회 fallback, 변경이 있으면 WAITING_FOR_PROVIDER.

## Approaches Considered

- **A 최소 핑 스케줄러** — 핑+원장+인증 게이트. 창 상태가 없어 P1에서 재구현 필요.
- **B 핑 + 창 상태 모델** — 선택(D6).
- **C 클라우드 예약** — 같은 5h 창을 여는지 미확인, v6 "클라우드 Job 생성 임의 구현 금지"와 충돌 → 제외.

## Recommended Approach — B

### 실행 모드 진리표 (R1-5)

| enabled | dry_run | --apply | 동작 | 원장 | exit |
|---|---|---|---|---|---|
| false | * | * | 판정만, 핑 0 | `quota_attempts`에 DISABLED | 0 |
| true | true | * | 판정만, 핑 0 | `quota_attempts`에 WOULD_PING / BLOCKED_* / SKIPPED_* | 0 (BLOCKED 있으면 3) |
| true | false | 없음 | 판정만, 핑 0 | `quota_attempts`에 WOULD_PING… | 0 / 3 |
| true | false | 있음 | 실핑 경로 | `quota_attempts` + `quota_slots` claim | 표 E |

`--apply` 단독으로 `enabled=false`나 `dry_run=true`를 넘지 못한다(S7).

### 원장 (R1-1, R1-6)

별도 SQLite `<state>/quota_window.sqlite3` (기존 ManagedStore와 분리, WAL, `busy_timeout=5000ms`, 모든 상태 전이는 `BEGIN IMMEDIATE` 트랜잭션).

- `quota_attempts(id, run_id, kst_date, trigger_id, provider, outcome, reason, created_at)` — 모든 실행의 판정 기록. **슬롯을 점유하지 않는다.** DISABLED, WOULD_PING, BLOCKED_AUTH, BLOCKED_BILLING, SKIPPED_LATE, SKIPPED_EARLY, DUPLICATE, FAILED 포함.
- `quota_slots(kst_date, trigger_id, provider, state, owner_pid, owner_run_id, started_at, finished_at, exit_code, reason)` PK(kst_date, trigger_id, provider) — **실핑 경로에서만** INSERT. state ∈ INTENT, SENT, LIMITED, UNKNOWN, FAILED.
- 따라서 dry-run이나 BLOCKED 이후 같은 트리거에서 `--apply`를 실행해도 정확히 1회 핑한다(S9).

### 트리거 시각 판정 (R1-4, R1-6)

- `delay = now_kst - scheduled_kst`. `delay < -60s` → SKIPPED_EARLY(시계 오차 1분까지는 정시로 본다).
- **T1 허용 지연**: `0700`은 `delay <= 5:00`(12:00 리셋과 12:05 사이 간격이 5분이므로), `1205`는 `delay <= 15:00`. 초과 시 SKIPPED_LATE를 `quota_attempts`에 provider별로 기록, 슬롯 미점유. 값은 설정 가능.
- `1205` 실행 시 같은 날 `0700` 슬롯이 SENT이고 `0700.started_at + window_hours > now`이면 핑은 그대로 보내되 결과를 `inside_open_window=true`로 기록하고 status에 "12:05 창이 고정되지 않음"으로 표시.

### 1회 실행 흐름

```
Windows Task Scheduler (등록은 별도 승인; P0는 명령 출력만)
  07:00 / 12:05 (OS 로컬시각; install-task가 KST→로컬 변환)
    └─ baton quota-window run --trigger 0700|1205 [--apply]
         ├─ now_kst = utc_now + 9h (clock 주입 가능)
         ├─ 시각 판정 → SKIPPED_EARLY / SKIPPED_LATE 이면 attempts 기록 후 종료
         ├─ 모드 판정(진리표) → 판정만이면 provider별 preflight 결과를 attempts에 기록 후 종료
         ├─ provider마다(순차):
         │    ├─ preflight(C1 인증, C2 과금 경로) 실패 → attempts BLOCKED_*, 슬롯 미점유
         │    ├─ 회수: 같은 슬롯이 INTENT이고 (now - started_at) > timeout+120s 또는 owner_pid 부재
         │    │        → UPDATE … SET state='UNKNOWN' WHERE state='INTENT'  (CAS)
         │    ├─ INSERT slot(state=INTENT, owner) ── PK 충돌 → attempts DUPLICATE, 0회
         │    ├─ COMMIT  ← 외부 호출 전 intent 확정
         │    ├─ ping (C3 명령, C4 timeout) 
         │    └─ UPDATE … SET state=<분류 결과> WHERE state='INTENT' AND owner_run_id=?  (CAS; 회수된 경우 덮어쓰지 않음)
         └─ JSON 결과 출력, exit 코드 표 E
  baton quota-window status → provider별 최근 슬롯, 창 추정(신뢰도 포함), 오늘 트리거 결과
```

### C1 인증 preflight (설치 버전 실측, 2026-11-03)

- Claude 2.1.317: `claude auth status` JSON. `loggedIn == true` 이고 `authMethod`가 구독 계열(`claude.ai`, `oauth_token`)일 때만 통과. `api_key`, `api_key_helper`, `third_party`, `none`, 필드 누락 → BLOCKED_AUTH/BLOCKED_BILLING. 현재 PC 실측값은 `loggedIn:false, authMethod:"none"` → 사용자가 `claude auth login` 하기 전까지 Claude 핑은 BLOCKED_AUTH.
- Codex 0.164.0: `codex login status` 출력이 `Logged in using ChatGPT`이면 통과, `API key` 등 그 외 → BLOCKED.

### C2 과금 경로 차단 (R1-10)

- 환경변수 존재 시 BLOCKED_BILLING: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `OPENAI_API_KEY`, `CODEX_API_KEY`.
- 핑 자식 프로세스는 위 변수를 제거한 환경으로 실행(이중 방어). 값은 기록하지 않고 이름과 존재 여부만 기록.
- Claude `apiKeyHelper` 설정과 Codex API key 로그인은 C1의 authMethod/로그인 상태로 판정.

### C3 핑 명령 (R1-11)

- cwd: 저장소 밖 전용 빈 폴더 `%LOCALAPPDATA%\baton\ping-cwd` (상위 폴더의 CLAUDE.md/AGENTS.md를 읽지 않게).
- Claude: `claude -p "hi" --output-format json --tools "" --strict-mcp-config --no-session-persistence --setting-sources user`
- Codex: `codex exec --ephemeral --skip-git-repo-check -s read-only -C <ping-cwd> "hi"`
- 정확한 인자 조합은 구현 첫 단계에서 설치 버전 `--help`로 재확인하고 fake runner 테스트로 고정한다.

### C4 timeout과 프로세스 트리 (R1-9)

- provider별 timeout 기본 120초. 기존 `baton.execution.run_process`(Windows 프로세스 트리 종료 구현 포함)를 재사용한다.
- timeout/kill 후 요청이 뒤늦게 처리될 수 있으므로 상태는 UNKNOWN, 재전송 금지.

### 결과 분류 (R1-7)

| 조건 | 상태 | 같은 슬롯 재시도 |
|---|---|---|
| exit 0 | SENT | 없음 |
| exit≠0, 출력이 `baton.execution.classify_error` = quota | LIMITED (창 이미 소진, 리셋 미상) | 없음 |
| 실행 파일 없음(FileNotFoundError), 인자 오류로 즉시 종료(요청 전) | FAILED (확실히 미전송) | 슬롯 삭제 후 같은 트리거 허용 지연 안에서 수동 재실행 1회 허용 |
| exit≠0, auth 분류 | FAILED + reason=auth | 위와 같음 |
| timeout, kill, 응답 유실, 그 외 exit≠0 | UNKNOWN | 없음 |

### 창 상태와 신뢰도 (R1-3, R1-14)

`quota_windows(provider PK, opened_at, expected_reset_at, confidence, source, observed_at)`

- SENT이고 직전 창 상태가 "닫힘 확인"(이전 expected_reset_at 경과)이면 `confidence=assumed`(A1 기반).
- SENT이지만 직전 창이 미상이거나 열려 있었을 수 있으면 `confidence=unverified`, status에 "수동 사용 시 다를 수 있음" 표시.
- LIMITED이면 `expected_reset_at=null`, `confidence=unknown`.
- status는 `assumed` / `unverified` / `unknown`을 문구로 구분하고 확정값처럼 보이지 않게 한다.

### 종료 코드 표 E (R1-8)

| exit | 의미 |
|---|---|
| 0 | 모든 provider가 SENT, 또는 판정만 모드에서 BLOCKED 없음, 또는 DISABLED |
| 3 | 하나 이상 BLOCKED_* / LIMITED / FAILED / UNKNOWN / SKIPPED_LATE (혼합 결과 포함) |
| 2 | 내부 오류(설정 파싱, DB 잠금 5초 초과, 상태 디렉터리 범위 위반) — 핑 0 |

### install-task 출력 (R1-12)

- `baton quota-window install-task --print`는 schtasks 명령/XML을 **출력만** 한다.
- OS 시간대가 UTC+9가 아니면 KST 07:00/12:05를 OS 로컬 시각으로 변환해 출력하고 경고를 함께 출력.
- 모드: "사용자가 로그온한 경우에만 실행"(구독 토큰이 사용자 프로필에 있어 암호 저장 방식 사용 안 함), python 절대 경로, 작업 폴더 고정.
- "절전 해제하여 실행" 끔(기본), "예약 시작을 놓친 경우 가능한 빨리 실행" 켬 — 늦은 실행은 T1 허용 지연 판정으로 SKIPPED_LATE 처리.

## Success Criteria

- S1 `enabled=false`: provider별 DISABLED 기록, 핑 0, exit 0.
- S2 같은 슬롯 재실행·동시 2프로세스: 추가 핑 0(DUPLICATE).
- S3 INTENT 후 kill/응답 유실 → UNKNOWN, 재전송 0. 살아 있는 INTENT(timeout 이내)는 회수하지 않음.
- S4 Claude 미로그인/`api_key`, Codex API key → BLOCKED_*, 핑 0. C2 환경변수 존재 → BLOCKED_BILLING, 핑 0.
- S5 `0700` 지연 5:00 → 처리, 5:01 → SKIPPED_LATE. `1205` 15:00 → 처리, 15:01 → SKIPPED_LATE. -61초 → SKIPPED_EARLY.
- S6 UTC 14:59/15:00 경계의 kst_date 정확, OS 시간대가 KST가 아니어도 동일.
- S7 `--apply` 단독으로 enabled=false/dry_run=true 무력화 불가.
- S8 기존 테스트 회귀 통과(기준: commit 2705fd3에서 `python -X utf8 -m unittest discover -s tests -t .` = 146 tests OK).
- S9 dry-run 후 같은 트리거 `--apply` → 정확히 1회 핑.
- S10 `0700`이 늦어 창이 12:05 이후까지 열려 있으면 `1205` 결과에 inside_open_window=true.
- S11 핑 자식 프로세스 환경에 C2 변수가 없음.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — consistency

**Problem**

> The run flow evaluates the trigger time (SKIPPED_EARLY/SKIPPED_LATE, then exit) before the mode check. With enabled=false, a late or early run therefore records SKIPPED_* and, per Table E, exits 3. The truth table row 'enabled=false -> DISABLED, exit 0' and S1 say every enabled=false run records DISABLED and exits 0.

**Remedy**

> Define the precedence explicitly. For example, evaluate enabled first so that enabled=false always records DISABLED and exits 0, or state that time-based skips take precedence and update the truth table, S1 and Table E. Add a test for a late run with enabled=false.

### R2-2 — clarity

**Problem**

> Table E is still incomplete. SKIPPED_EARLY and DUPLICATE appear in neither the exit-0 row nor the exit-3 row. A mixed result such as SENT plus DUPLICATE is unmapped. For judgment-only mode, the truth table says '0 (3 if BLOCKED)' while Table E's exit-3 row also lists SKIPPED_LATE, so the exit code of a dry-run late run is ambiguous.

**Remedy**

> Give an exit code for every outcome (DISABLED, WOULD_PING, BLOCKED_*, SKIPPED_EARLY, SKIPPED_LATE, DUPLICATE, SENT, LIMITED, FAILED, UNKNOWN, internal error) and a rule for aggregating mixed per-provider results, and make the truth table refer to that single table.

### R2-3 — feasibility

**Problem**

> C2/C4 commit to reusing baton.execution.run_process and to launching the ping 'with the C2 variables removed' (S11). The actual run_process builds its environment as dict(os.environ, ...) and applies env_overrides with update(). Variables can therefore be added or overwritten but never removed, and setting one to an empty string may still count as present to the CLI. The sanitized-environment guarantee cannot be met with run_process as it stands.

**Remedy**

> Specify a run_process change, such as an env_remove parameter or a fully supplied environment, or a dedicated launcher for the ping. Make S11 assert that the variables are absent (not empty) in the child environment.

### R2-4 — completeness

**Problem**

> The API-billing path detection still covers only process environment variables and the CLI login status. It leaves out config-file and other routing paths. Examples: an env block in the Claude user settings (~/.claude/settings.json, which --setting-sources user still loads) setting ANTHROPIC_API_KEY or ANTHROPIC_BASE_URL; other routing variables such as ANTHROPIC_BASE_URL and CLAUDE_CODE_USE_FOUNDRY; and a Codex config.toml model_provider or API-key preference that routes requests away from the ChatGPT subscription even when 'codex login status' reports ChatGPT.

**Remedy**

> Enumerate the config files and keys per provider that count as a billing or routing path (Claude settings env/apiKeyHelper, Codex config.toml model_provider and auth preference, base-URL overrides), block on any of them, and add fixture tests for each.

### R2-5 — feasibility

**Problem**

> The outcome classifier relies on the generic baton.execution.classify_error. Its quota markers (for example 'usage limit reached' and 'insufficient_quota') are not verified against the actual Claude Pro and Codex subscription-limit messages, so a real limit may fall through to UNKNOWN. The FAILED row 'argument error that exits immediately (before the request)' has no detection input, because classify_error has no such category. Whether the network, rate_limit and permission categories map to FAILED or UNKNOWN is left implicit in 'other exit≠0'. Exit 0 is mapped to SENT without checking the JSON error field from --output-format json.

**Remedy**

> Specify a per-provider classifier: exit codes, stdout/stderr or JSON fields, and the subscription-limit and auth message patterns captured from the installed CLI versions as fixtures. Give an explicit mapping for each classify_error category. Say how 'definitely not sent' is proven, or drop the argument-error FAILED case.

### R2-6 — clarity

**Problem**

> The FAILED retry policy 'delete the slot, then allow one manual rerun within the trigger tolerance' does not say who deletes the slot (an automatic step on FAILED, or a user command and which one). It does not say how the 'one' rerun limit is enforced once the PK row has been deleted, or how the deleted FAILED record is preserved for audit.

**Remedy**

> Define the mechanism, for example a conditional transition FAILED -> retry-allowed with a retry_count column, or a `baton quota-window retry` command. Enforce the one-retry limit in the schema, keep the original FAILED record in quota_attempts, and add a test.

### R2-7 — feasibility

**Problem**

> The ping invocation still omits a committed model and reasoning effort for both CLIs. The provider default (for example a large model or a high reasoning effort) may consume far more of the window than intended. For Codex, '-s read-only' restricts writes but does not prevent the agent from running shell commands or tool turns. The expected minimal output that counts as success is not defined. User-level memory (~/.claude/CLAUDE.md, ~/.codex/AGENTS.md) may still load despite the dedicated cwd.

**Remedy**

> Commit the model and effort flags per provider, a tool or turn limit for Codex (or the documented way to get a single response with no tool use), the expected output shape for SENT, and whether user-level memory is acceptable. Then verify them in Next Step 1.

### R2-8 — consistency

**Problem**

> The two-window promise has zero margin in normal operation. The 0700 tolerance (5:00) equals the 12:00 to 12:05 gap, and the 1205 trigger is accepted up to 60 s early. Providers run sequentially with a 120 s timeout each, so the second provider's ping can start minutes after the delay was evaluated, and request latency adds more. A 0700 ping on the edge of tolerance plus an early 1205 run therefore lands inside the open window, by design rather than as an exception.

**Remedy**

> Evaluate the delay per provider immediately before its ping, and give a safety margin. For example, make the 0700 tolerance plus ping latency smaller than the gap minus the early tolerance, or derive the 1205 run time from the actual 0700 SENT time. Add a success criterion for the slowest valid 0700 run combined with the earliest valid 1205 run.

### R2-9 — feasibility

**Problem**

> The inside_open_window check uses '0700.started_at + window_hours > now'. started_at is recorded before the ping, and the window actually opens when the server receives the request, which is later. So a 1205 run shortly after started_at+5h is reported as not inside the window while it may still be open. The check also considers only a SENT 0700 slot, while a 0700 UNKNOWN (timeout or kill, possibly delivered) can likewise leave the window open.

**Remedy**

> Use a conservative bound (finished_at, or started_at plus timeout) for the window start, and treat a same-day 0700 UNKNOWN as possibly open (inside_open_window=unknown). Add tests for both.

### R2-10 — completeness

**Problem**

> The rules for updating quota_windows cover only SENT and LIMITED. They do not say what happens to the window row when the 1205 ping is SENT with inside_open_window=true (it must not move expected_reset_at under A2), or on UNKNOWN or FAILED. inside_open_window is also not a column in any of the defined tables (quota_attempts, quota_slots, quota_windows), so where it is stored is unspecified.

**Remedy**

> Define the quota_windows transition for every slot outcome, including SENT inside an open window, and add the inside_open_window column (or reason encoding) to the quota_slots schema.

### R2-11 — consistency

**Problem**

> 'Closure confirmed' is defined as the previous expected_reset_at having elapsed. BATON cannot see manual use, though: a manual chat at 05:00 opens a window until 10:00, so the 07:00 ping lands inside it, yet the row gets confidence=assumed. The label overstates what is known, which works against Problem Statement/Premise 2 (manual use) and the goal of not looking confirmed.

**Remedy**

> Rename the condition to something like 'BATON-tracked window elapsed' and state that manual use is not observed. Either lower the confidence of such rows or make the status wording say that manual use outside BATON can invalidate the 'assumed' estimate.

### R2-12 — consistency

**Problem**

> Table E states that exit 2 (internal error, including a DB lock held for more than 5 s) means 'ping 0'. A lock or DB error can occur at the post-ping CAS UPDATE, after the external request was sent. The ping count is then 1 and the slot stays INTENT, and the behavior and exit code for this case are unspecified.

**Remedy**

> Separate pre-ping internal errors (ping 0) from post-ping persistence failures. Specify the latter's outcome (slot left INTENT and later recovered to UNKNOWN, never resent), its exit code and its stderr reporting, and add a test.

### R2-13 — feasibility

**Problem**

> install-task converts KST 07:00 and 12:05 to fixed OS-local times when the OS is not UTC+9. If the OS time zone observes DST, a fixed local trigger drifts by an hour across a DST transition. The task would then fire at the wrong KST time, and every run would become SKIPPED_EARLY or SKIPPED_LATE until it is reinstalled.

**Remedy**

> State the behavior for DST-observing OS time zones: refuse and warn, emit triggers per DST period, or require the OS to be on KST. Add an S6-style test for the printed output.
