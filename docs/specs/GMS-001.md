## GMS-001-REQ-01 Local credential storage

### GMS-001-AC-01

API keys are stored encrypted in a local vault whose master key stays in the OS key store. Plaintext is never written to the database, and a missing key store or tampered ciphertext fails closed.

### GMS-001-AC-02

The local management server rejects state changes without a valid CSRF token and does not echo secrets or input in responses.

## GMS-001-REQ-02 Two independent gates

### GMS-001-AC-03

The GMS switch defaults to off, can be turned on only with a saved key and limits, and off blocks new quotes. Turning it off keeps saved limits.

### GMS-001-AC-04

The GMS provider is registered only with `--enable-gms`. Even when registered, nothing is sent while the switch is off or the local server is down, for direct and fallback use alike.

## GMS-001-REQ-03 Budget safety

### GMS-001-AC-05

Reserve floors and token caps stop generation before a request is sent. Uncertain reservations survive restart, and an uncertain dispatch is never retried automatically. GMS output remains a draft that requires manual application.

## GMS-001-REQ-04 Migration and packaging

### GMS-001-AC-06

The Jipdam vault import is a one-time copy: the original is unchanged, key IDs are kept, GMS arrives off, and existing BATON data is never overwritten.

### GMS-001-AC-07

`cryptography` is the optional `gms` extra. Without it, base BATON works, credential commands report `gms_extra_required`, and the GMS provider sends nothing.
