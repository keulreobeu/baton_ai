# BATON 운영 정책

Setup을 진행하는 AI는 기본 실행 환경 구성 뒤 아래 조합을 사용한다. 사용자의 최초 화면에는 [SETUP의 여섯 선택지](../SETUP.md)만 보여 준다. 기존 프로젝트에서 명시적으로 끈 로드맵은 그대로 보존한다. 이전의 4프로필 이름이나 off를 신규 값으로 조용히 변환하지 않는다. 새 조합으로 이전하기 원하는 경우 달라지는 의무를 알리고 사용자가 선택한 변경만 반영한다.

| 프리셋 | Roadmap | SDD | Review | Validation | Checker |
|---|---|---|---|---|---|
| 자율 개발 | Auto | Free | Auto | Auto | Auto |
| 기본 개발 | Auto | Free | Auto | Merge | Auto |
| 경량 SDD | Basic | Lite | Auto | Task | Auto |
| 관리형 SDD | Managed | Managed | Auto | Task | Auto |
| 정식 SDD | 기존 계약 | 기존 계약 | 기존 계약 | 기존 계약 | 기존 계약 |

상세 설정은 다섯 값을 독립적으로 정한다. 예를 들어 Managed 로드맵에 Free SDD, Cross 검토에 Auto 검증도 가능하다. 사용자 선택은 프로젝트 필수 CI·승인·안전·브랜치 보호를 보존한다. Full은 해당 프로젝트가 채택한 정식 계약을 가리킨다. 승인된 계약을 찾지 못하면 선택은 유지하고 ‘구성 미완료’로 둔다. BATON 자체에서 Full은 BATON SDD·등급별 문서·독립 검토·V1/V2/V3·승인·원격 CI를 그대로 따른다.

## Roadmap — 목표와 순서

**Auto**는 생성·관리 여부를 AI가 판단한다. **Basic**은 목표, 마일스톤과 달성 조건, 진행 상태를 기록한다. **Managed**는 여기에 우선순위, 해당 시 의존성, 보류·차단, 목표 변경 이력을 더하고 필요할 때 다음 작업을 제안한다. 기존 보드·계획을 우선 사용한다.

로드맵 관리를 시작하면 README·기존 구상·SDD·Plan·Task·Issue·Git 전달 근거를 필요한 만큼 읽는다. 근거가 충돌하면 출처별 차이를 묻고, 비면 “이미 생각해 둔 목표나 먼저 해결하고 싶은 문제가 있나요?”라고 묻는다. 예를 들어 로컬 복원만 검증된 프로젝트에서는 “다음 PC에서 이어가기까지를 첫 성과로 잡을까요?”라고 묻는다. 목표와 지금·다음·이후의 사용자 성과, 순서의 이유, 판정 기준, 원본 링크를 초안으로 보여 주고 사용자와 수정한다. 합의, AI 제안, 미정 항목을 구분한다.

일반 커밋에는 갱신을 요구하지 않는다. 개별 Task 완료는 원본에서 기록한다. 기능 완료·마일스톤 달성·중요 차단·우선순위 또는 목표 변경 시 코디네이터가 해당 성과만 갱신한다. Worker는 자기 Task에 필요한 목표 참조만 받는다. 단기 수정은 필요할 때만 연결한다. 중단된 초안과 경로는 다음 대화에 재사용하고 사용 중단 시 기존 문서를 보존한다. 로드맵 순서와 실행 승인은 따로 확인한다.

## SDD — 작업 정보를 어디에 남길지

| 선택 | 필요한 정보와 재개 방법 |
|---|---|
| Free | 정식 산출물 의무가 없다. 작업 요청과 대화에서 범위를 파악한다. |
| Lite | 요구·짧은 구현 계획·관찰 가능한 수락 기준·Task 상태·최소 재개 정보를 기존 Issue나 한 문서에 모을 수 있다. 파일 분할은 AI가 결정한다. |
| Managed | Lite 정보에 중요한 설계 결정과 변경 이력, 적용 가능한 작업 의존성, 차단 조건과 다음 담당자가 이어갈 정보를 더한다. |
| Full | 채택한 계약에서 지정한 문서·게이트·승인에 연결한다. 계약 안에 묶인 검토·검증 의무도 유지한다. |

## Review — 누가 언제 검토할지

사용자와 합의한 작업 단위의 완료 시점에 적용한다. 사전 설계 검토는 선택한 기존 계약의 필수 조건을 우선하고 그 밖에서는 AI가 판단한다. **Auto**는 자율, **Self**는 작성자 자체 검토, **Independent**는 자체 검토 후 작성 실행과 분리된 검토자, **Cross**는 자체 검토 → 내부 독립 검토 → 그 시점의 필수 내부 검증 → 다른 공급자 검토 순서다. 작성자의 이름·페르소나만 변경해 독립성을 주장할 수 없다. Cross+Validation Auto는 실행 검증을 새로 의무화하지 않는다. 필요한 검토자를 쓸 수 없으면 해당 판정을 미완료로 보고한다.

검토자·후보·범위·결과·차단점을 기존 기록에 남긴다. 수정 후 변경 지점과 직접 회귀 범위만 다시 보며, 동일 후보의 유효 결과는 프로젝트 정책 안에서 인용한다. 같은 원인이 반복되면 접근을 바꾸고 실질적 진전이 없거나 권한·비용 한계에 이르면 남은 조건과 함께 중단한다. Full 계약의 반복·재사용 규칙을 적용한다.

## Validation과 Checker — 실행할 시점과 도구

| Validation | 필수 실행 검증 시점 | Checker Auto | Checker Required |
|---|---|---|---|
| Auto | AI 판단 | AI 판단 | 작업 완료 전 |
| Merge | 통합 브랜치 반영 전 | AI 판단 | 통합 전 |
| Task | 작업 완료와 통합 전 | AI 판단 | 작업 완료와 통합 전 |
| Full | 기존 계약 | 기존 계약 | 기존 계약 |

Free SDD에서도 사용자 요청을 작업 단위로 삼을 수 있다. 완료는 담당자가 합의한 작업 완료를 선언하는 시점이다. 통합은 병합 또는 승인된 직접 반영으로 프로젝트의 통합 브랜치를 갱신하기 직전이다. 브랜치 반영이 없으면 통합 이벤트도 없다. 장애·차단·중간 보고는 언제든 가능하다.

필수 시점마다 변경에 적합한 방법·범위·충분성은 AI가 판단하고 실제 실행한 결과만 남긴다. 예를 들어 CSV 내보내기라면 현재 후보에서 새로 만든 파일의 BOM과 열 순서를 확인한다. 대상 브랜치가 바뀌거나 새 base에서 CSV 생성기가 달라지면 새 통합 후보에서 관련 부분을 확인한다. 후보 내용·비교 base·적용 범위·환경·목적이 유효하고 프로젝트가 허용할 때 결과를 재사용한다. 불분명하면 다시 실행한다. 필수 원격 CI와 기존 no-skip·재사용 금지는 그대로 따른다.

Checker Required는 대상 프로젝트 루트에서 관련성이 있는 **신뢰된 요청**에 BATON INPUT_CHECK를 사용한다. 예를 들어 `baton input-check --request .local_runtime/input/request.json`은 파일·Git·환경을 확인하고 tests/sdd의 실제 실행은 `--execute`를 명시해야 한다. 요청에 임의 명령을 넣지 않는다. 내장 sdd 검사의 base는 `origin/main`이어서 다른 통합 branch·Task base에 무조건 사용할 수 없다. Node 프로젝트의 JSON 형식 PASS는 JS 동작 검증과 별개이므로 해당 제품 테스트 결과를 따로 연결한다. 적용 가능한 신뢰 요청이 없으면 ‘필수 검사 미구성’, FAIL·BLOCKED·UNKNOWN·NOT_RUN은 해당 상태로 남긴다. Required를 자동으로 Auto로 내리지 않는다. 같은 과정으로 두 의무를 실제 충족했다면 한 번 기록한다. [INPUT_CHECK 계약](https://github.com/keulreobeu/baton_ai/blob/8fb4e82747442e22bfc79ef7ab1643a7a67115b0/docs/harness/INPUT_CHECK.md)

구현 완료, 자체·독립 검토 결과, 실제 검증·미실행, 작업 완료, 병합 가능을 구별해 보고한다. 해당 시점의 필수 조건을 충족하지 못하면 그 단계만 보류하고 무엇을 확인하면 재개할지 적는다. 사람이 직접 하는 병합은 프로젝트에 설정된 권한과 보호 규칙이 담당한다.
